# 求解器阶段 1：逐小时 N-1 可交付容量

## 1. 目的

阶段 0 只在 5 个合成负荷水平上测了容量，够用来评估成本，不够用：D/E 评价链需要**逐小时**的 `supply_mw`。本阶段把真实 RTS-GMLC 负荷时序接到 DC OPF 上，产出可被评价链直接读取的容量表。

## 2. 声明的映射规则（跑前固定）

RTS-24 算例自带参考负荷（24 母线共 2850 MW），观测时序的量级不同。桥接方式是保形缩放：

$$
\text{case\_load}_h = \text{case\_reference} \times \frac{\text{observed\_load}_h}{\overline{\text{observed\_load}}}
$$

**逐小时形状是实测的，量级固定在算例自身的参考值上。** 不做拟合、不在看到结果后调整任何小时。

窗口：8784 小时中的 h0–h167（一周）。

**可行性规则**：RTS-24 全部机组最小出力 1036 MW、最大出力 3405 MW。缩放后负荷落在该区间外的小时标记 `evaluable=false` 并如实报告，不丢弃。

## 4. 两次测量错误的更正（必须记录）

本阶段产生了 attempt_01–03，前两个是分类器错误，**结果作废**，保留不删。

**错误一：把"抬高负荷至可行"当作容量。** 阶段 0 已记录过同类问题（负荷低于机组最小出力时，最大化注入的 LP 测的是"最少加多少负荷才可行"）。本阶段在 5 个超上限小时上遇到了对偶情形，已用 `evaluable=false` 隔离。

**错误二：按小时判断"发电受限"，漏判 66 个小时。** 初版规则是"若五个 POI 的 base 容量完全相同且等于 `pmax − load`，则该小时发电受限"。这个规则在 H19 失效：

```
H19  case_load 3187.7, pmax - load = 217.3
poi  3  base 208.4   ← 不同
poi  7  base 217.3   ← 等于发电余量
poi 15  base 217.3
poi 19  base 217.3
poi 23  base 217.3
```

五个 POI 的**断电容差**不同，基准工况的绑定对象因此不同，容量并不全等。按小时判断只找到 15 个小时，按行判断找到 252 行 / 81 个小时。已改为**逐行判断**：某行 base 容量等于 `pmax − load` 即标为发电受限。

这个错误的后果是实质性的：未修正时母线 15 的"最小值"被算成 57.1 MW（实为发电受限行），修正后为 392.8 MW。

## 5. 对论文的影响

**第一，`supply_mw` 现在可以逐小时给出，且带物理来源。** 原来是一个声明常数，现在是"给定网络、机组与 N-1 故障集下该母线可实际送达的功率"。

**第二，选址效应被量化。** 同一网络内，站点选择使可用容量相差约 6 倍。这个差异在原设定里完全不可见。

**第三，可用容量随时间波动。** 网络受限行的极差为 1.4–2.1 倍，由真实负荷时序驱动。这为"阶段比较"提供了真实的时变约束。

## 6. 限制

1. **DC 近似**，无 AC 可行性、无电压/无功约束（`ac_certified=false`）。
2. **N-1 为逐支路独立断开**，不是联合故障集。
3. **负荷等比缩放**，未模拟分区负荷差异。
4. **未接入机组组合**：每个小时独立求解，没有跨时段状态（启停、爬坡、储能）。阶段 2 的 SCUC 才处理这些。
5. **单一 slack 母线**。
6. 窗口只取 h0–h167；全年 8784 小时的完整扫描未做（成本约 3.5 小时）。
