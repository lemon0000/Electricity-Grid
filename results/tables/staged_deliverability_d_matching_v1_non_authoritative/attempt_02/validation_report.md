## 1. 为什么另建匹配臂

D 合同 §4 为 6.2 登记了"恢复时段匹配臂"，attempt_01 未跑。而 D 主网格的 `early`/`late` 不能替代：二者总量同为 `317/50`、峰值同为 `26/25`，但 `late` 在 h2 的清洁额度为 `16/25`、`early` 为 `21/25`，h2 的 CFE 请求分别是 `1/4` 与 `0`。任何判定差异都不能归因于到达时段。

`test_d_early_late_do_not_satisfy_the_match` 以测试固定了这一点。

## 2. 匹配设计

三条清洁路径：

```
h0, h1 : 3/5, 1/2          与 D 相同（保留低清洁结构性小时）
h2..h7 : 21/25             该值下 CFE 请求恰为 0
其中一小时 : 26/25          唯一的恢复余量来源，位置分别为 h3 / h4 / h5
```

验证的匹配性质（执行器内 `match_checks`，`match_problems: []`）：

- 总量均为 `317/50`；
- 峰值均为 `26/25`，且每臂恰有一个高清洁小时；
- **逐小时 CFE 与电网请求完全相同**（由 `request_profile` 逐小时记录，测试逐项比对）；
- 参数、设备、业务路径、电网配置与 D fixture 逐字节相同。

改变的只有**恢复余量出现的时点**。

## 4. 机制

`fast` 在 h1 产生 `1/5` 即时延期（电网临时限额 `5/8`），期限 h3（`deadline_lag=2`）。匹配臂中恢复余量只出现在一个高清洁小时：

| 到达 | 完整时序恢复时点 | 期限结局 | 定值 |
|---|---|---|---|
| h3 | h3（恰在期限小时） | `missed_at_deadline=0` | 可交付 |
| h4 | h4 | 补做完成，逾期 `1/5` 保留 | 不可交付 |
| h5 | h5 | 同上 | 不可交付 |

期限当小时的补做仍算按时，晚一小时即记为逾期。轨迹逐小时核对：h3 臂在 h3 回收 `1/5`，cohort `(4, remaining=0, missed=0)`；h4/h5 臂分别到 h4/h5 才回收，cohort `(4, remaining=0, missed=1/5)`。

**对简化评价的连带后果**：h4/h5 时参考方判失败，而 `instantaneous` 与 `fixed_headroom` 仍判可交付，策略轴因此从 D3 变成 D1。策略轴 D1 由 6 增至 10，重放轴 D1 恒为 12（方法自身安排未变）。

## 5. 不随到达时段变化的单元

| 单元族 | 原因 |
|---|---|
| `fast/delayed` | h2 触发 `grid_service_shortfall` 即停止，与恢复时点无关；该组合在任何到达位置都没有正恢复余量 |
| `slow/on_time` | h2 供电 `13/10`、参考 `4/5`，基线 `21/25` 已留下 `1/5` 余量；业务 h5 才达产，移动高清洁小时不改变结果 |
| `slow/delayed` | 恢复余量首次出现在 h4，已晚于 h3 期限，三臂恒为不可交付（由电网投运时点决定，不由清洁到达决定） |
