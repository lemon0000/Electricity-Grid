## 3. 本会话修的两个 bug

### 3.1 `proxy_evidence` 链式传参（已由真实链路验证）

repair-005 起每一层 `_validate_round_artifacts` 进入时解包 `evidence["proxy_evidence"]`，但向父层只传解包后的子映射，导致下一层 `KeyError('proxy_evidence')`。repair-005~008 都在候选 5 之前失败或中断，从未执行到该路径，缺陷潜伏至今；**repair-009 是第一个真正走到候选 5 保存逻辑的版本**。

修法：在 runner-009 里按中间祖先层数（repair-007 → 006 → 005，共 3 层）嵌套包装真实 proxy evidence，`cost_evidence` 每层随行。repair-004 是叶子，直接消费 proxy 映射。

**验证**：候选 5 检查点成功落盘，`checkpoint_manifest_sha256 = a1bacf3706d7239aebdd1018c593675a2ea3e29c301a330e4bf64bb6d9d22aa9`。这是真实链路验证，不只是单测。

### 3.2 Gurobi 不可行通道缺失（**仅合成单测，真实链路未验证**）

`src/grid/rts_gmlc_formal_cg_adapter.py:239-245` 判定 `globally_infeasible` 时硬编码 `solver_api == "pyomo.contrib.solver.highs_v2"`。Gurobi 实报 `gurobi_legacy` + `termination_condition=minFunctionValue` + `solver_status=aborted`，条件永不成立 → `globally_infeasible` 恒为 False → level_set 二分法两个分支都推不动（既无可行 incumbent 抬下界，也无不可行证书压上界）→ `decision_mip_unresolved_without_feasible_incumbent` → `strict_cost_separation_not_proven`。

候选 6 的实测数值：`proxy_floor = 0.6495756718528995`，`Cutoff = 1,163,877.341735611`，根节点对偶界 `1,163,877.341851999`，超出 **1.16e-4 USD**（相对约 1e-10），Gurobi 剪掉整棵树，`Solution count 0`。

修法：runner-009 monkeypatch 包装 `solve_master`，在 stage 为 `level_set_budget_feasibility`、求解器为 Gurobi、无可行 incumbent、且对偶界严格超预算上限时置 `globally_infeasible=True`，与 HiGHS 的 `provenInfeasible` 同等对待。**未额外加数值裕度门槛**——加了等于我擅自提高科学标准，而基线从未对 HiGHS 的证明要求过裕度。`timeLimit` 终止被明确排除，符合 `timeout_or_ambiguous_is_infeasibility_evidence: false`。超出裕度写入 `decision_mip` 供审计。

**验证状态：8/8 合成单测通过**（含候选 6 真实数值 + 7 个必须不触发的负例：界未超上限、HiGHS 路径、错误 stage、有可行解、timeLimit 终止、界非有限、上限为 None）。**真实链路验证点是候选 6，尚未取得。这是当前唯一真正未知的东西。**

### 附带发现

`strict_cost_separation_margin_usd: 1.0e-4` 对 116 万美元量级成本是 1e-10 相对精度，低于任何 MIP 求解器的可信分辨率。该参数本身值得重新审视，不只是候选 6 的问题。

### 设计要点（保留）

- 规模：3 个 commitment 源（零 DC 基线 / 候选 1 / 候选 5）× 3 小时（h0 对照 + h15 + h21）× 3 初值（`source` / `midpoint` / `flat_target_midq`）= 27 次 IPOPT 求解
- 硬自检：用零 DC 基线 commitment 跑同一路径，必须复现已发表的 h15/h21 未见证结论；`summary.json` 写 `harness_reproduces_published_baseline`，为 false 则整轮结果无效。**没有这层防护，一个有 bug 的 harness 报出「候选通过」最容易被接受**
- `_witness` 判定从已发表诊断逐字移植：五项违约 ≤1e-6 加收敛与求解成功，确保与 `blocker_register.md` 的 witness 含义一致
- 数据中心注入恒为 0 MW，与已发表零 DC 对照同边界
- 按项目惯例需自己的预注册与 manifest；口径是 diagnostic sensitivity，不是安全认证

### CPU 竞争

27 次 IPOPT（每次上限 600 s）会与候选生成抢机器。候选生成预热阶段是单核满载，建议等它进入 Gurobi 4 线程阶段再跑 AC 对照，或先暂停候选生成。
