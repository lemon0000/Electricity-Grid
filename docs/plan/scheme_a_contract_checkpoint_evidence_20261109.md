# 方案A：接入协议、保存机制与最近邻核查

2026-11-09。DRAFT_NONAUTHORITATIVE；定向来源核查，不是系统查新、正式结果或模型变更。本轮未运行实验、solver或下载外部数据集。既有探针与失败记录保持原样。

## 判断

方案A有真实合同基础，可以继续作为候选问题。此次找到的依据比泛称“柔性接入”更具体：官方文本同时包含Firm保障下限、响应期限、恢复约束和分阶段接入模板。但现有合成探针尚不能证明真实合同下的通知—Firm替代幅度：低Firm同时触发强制关闭/回滚，是探针的控制假设，不是进口功率限制自动推出的结论。

因此现阶段可研究的问题应是：给定阶段接入权利、任务状态及可执行的降载/保活/保存措施，业务可履约的合同边界在哪里？是否能得到有适用条件的替代边界，仍需验证。不得写成已达到TSG标准。

## 一、官方合同证据

### ESB Networks：分层与升级转刚性

[Dynamic Flexible Demand Connection官方说明](https://www.esbnetworks.ie/services/optimise-my-energy-use/beat-the-peak-programme/commercial/flexible-demand-connections)明确描述：暂时的柔性接入在相关网络升级后成为刚性接入；约束期降低到Firm MIC。网页以2 MVA Firm加1 MVA Flexible说明权利分层。

网页没有给出通知提前量、响应截止时间、事件长度/频率或工程实际完工日期。MVA不能直接当MW，必须说明功率因数。该网页支持合同结构，不能校准我们合成菜单的容量比例或可购买通知档位。

### EirGrid：有明确响应规则的公开协议模板

[Flexible Demand Operating Protocol，2024版](https://cms.eirgrid.ie/sites/default/files/publications/Flexible-Demand-Operating-Protocol-October-2024.pdf)，修订表为2024-09-25 v3.0。核对正文§2.1—2.3及附录1—2：

- §2.1：设定值不低于Firm MIC的MW等值；收到指令后2分钟内确认，确认后5分钟内达到设定值。
- §2.2：解除后允许在1小时内恢复，并受约定爬坡率和分步设定约束。
- §2.3：未按要求降载可能导致系统运营者断开接入；这不同于合规削减本身要求关闭计算任务。
- 附录包含分阶段接入及容量/爬坡栏，但明确标为示例，需由站点数据替换。

这是通用模板，客户名/签署项待填；不是已签署数据中心协议。它不能自动被认定为上述ESB产品在某个站点的适用附件。模板响应时间也不能解释为预先获得事件信息的时间，或把2+5分钟作为固定通知期。

## 二、checkpoint证据及参数含义

[PyTorch与IBM/Meta官方技术说明](https://pytorch.org/blog/reducing-checkpointing-times/)报告7B模型同步保存平均GPU停顿148.8秒，异步方案为6.3秒。其架构将GPU到CPU暂存与CPU到磁盘持久化分开，异步方案缩短训练停顿，不表示完整落盘在6.3秒完成。

需要分别记录GPU停顿、暂存、持久化和恢复耗时，以及各阶段必须供电的GPU/CPU/内存/存储范围。该来源没有提供我们站点的保活功率、恢复功率曲线或任务SLA；不能直接替换成一套已校准参数。原探针5分钟槽和10分钟保存为合成假设，可能无法解析秒级暂存与分钟级响应的关系。

关键机制缺口是：降载后是否仍能维持进程/内存、完成异步落盘，或通过其他措施保护状态？只有在声明可用控制后仍无法保护状态时，才有依据计入强制回滚。应同时报告无回滚、状态保留和确需终止的区域，不能只选择有损区域。

## 四、下一轮验证的最小范围

下一轮应先固定控制语义，再运行有界诊断：

1. 所有方法共享同一进口功率轨迹、响应截止时间、任务原期限和通知前历史；容量变化与控制手段分别作为比较因素。
2. 显式区分继续低功率执行、暂停保活、异步暂存/落盘与终止回滚。参数缺证据的项保留假设标签及透明范围。
3. 分别比较完整任务状态模型与省略状态的容量模型，并保留拥有相同控制手段和信息的强调度基线。
4. 检验有损机制是否在合理保活条件下仍存在，能否改变接入/业务接纳决策；也记录保活消除差异、通知无价值和不可履约的区域。

若差异只能靠人为规定“低Firm必关机”维持，应收缩或放弃该回滚主张。若显式保活后仍出现稳定边界，再考虑多任务、网络与阶段工程扩展。此处仅提出验证设计；尚未修改运行合同或启动新实验，实验准入仍按agent.md §9执行。
