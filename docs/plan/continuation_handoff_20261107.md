## 4. 三个测量错误（新会话必须知道，否则会重犯）

这三处都是会污染论文的，且都是在自查中发现的，不是外部指出。

### 错误一：DC OPF 功率平衡符号

初版把负荷项符号写反，导致 `NoFeasibleSolutionError`。正确形式（母线 b）：

```
Σ_g p_g − Σ_{l: f_l=b} f_l + Σ_{l: t_l=b} f_l − d_b = 0
```

修正后单小时 0.031 秒求解。

### 错误二：把"抬高负荷至可行"当作可交付容量

当负荷低于机组最小出力时，最大化注入的 LP 会**增加负荷来把系统抬出不可行区**，测出的不是转移能力，而是"最少需要加多少负荷才可行"。

- 阶段 0：0.35 倍负荷档得到 324 MW 的伪值。
- 处理：阶段 0 改为从 0.40 起测并记录下界；阶段 1 对超上限小时标 `evaluable=false`，如实报告不丢弃。

### 错误三：按小时判断"发电受限"，漏判 66 个小时

初版规则："若五个 POI 的 base 容量完全相同且等于 `pmax − load`，该小时发电受限。"

在 H19 失效：

```
H19  case_load 3187.7, pmax − load = 217.3
poi  3  base 208.4   ← 不同
poi  7  base 217.3
poi 15  base 217.3
poi 19  base 217.3
poi 23  base 217.3
```

各 POI 的**断电容差不同**，基准工况的绑定对象因此不同，容量并不全等。按小时判断只找到 15 个小时，按行判断找到 252 行 / 81 个小时。

**已改为逐行判断**：某行 base 容量等于 `pmax − load` 即标 `limited_by="generation"`。

后果是实质性的：未修正时母线 15 的 N-1 最小值被算成 57.1 MW（实为发电受限行），修正后为 392.8 MW。

**attempt_01 与 attempt_02 是这两处分类器的作废结果，保留供追溯；attempt_03 有效。**

### 5.1 两条判据的推导与验证（结论尚未入库）

**判据 A（恢复窗口）**：任务 $j$ 的可用恢复余量在 $[a_j, d_j]$ 内累计不足其延期工作量 → 必逾期。

- 外生版本：`phys_h = min(capacity, max_recovery, compute−workload, (supply−ref)/slope, (clean/α−ref)/slope)`，只统计无延期请求的小时，累计 `phys_h × eta` 与债务比较。
- 验证：D 6/6、敏感性 27/27、E 6/6 = **39/39**。

**判据 B（余量越界）**：方法自身发出的恢复指令超过该小时的物理可用余量 → 重放必报 `recovery_headroom`。

- 验证：fixed_headroom 39/39（限实际重放到的小时；未重放的小时属截断，不计）。
- 关键：必须**限定在实际执行到的小时**，否则会把因提前停止而未执行的指令算作误报。

**否定结果（重要）**：判据 A **不能**单独预测 D1。D 网格 16 单元中错 4，准确率 75%。原因：D1 还有违约码通道（`fixed_headroom` 的 `recovery_headroom`/`scalar_supply`），判据 A 完全不覆盖。

**论文措辞约束**：不得写成"提出预测假通过的判据"。正确写法是"简化评价在两种可判定的条件下失效"，且每条判据只对其通道负责。

**证伪过程中的一个陷阱**：初版判据用 `advance()` 的 `limit`（含 `debt/eta`）得到 100%，那是**同义反复**——`advance()` 用的就是同一公式。必须去掉全部内生项（债务、记录、任何策略产物）才构成独立预测。

### 5.2 RTS-24 首次接入失败的根因

`experiments/rts24_deliverability_adapter_v1.py` 第一版把所有证据标成 D4（14/15 退化）。根因两条：

1. 把 `cfe_contract: eligible_resource_universe_not_allocated_portfolio` 当作**已分配给站点的组合**。数据自己的 `summary.json` 明确这是"合格资源池"，不是站点持仓。
2. `α × reference` 的瞬时 CFE 约束与真实风电不兼容：站点参考负荷约 375 MW，`α=4/5` 要求每小时约 312 MW 清洁电量，而真实风电夜间掉到 0–6 MW，多数小时结构性不可行。

**该文件是失败探针，未提交，不要当作证据引用。** 重做时按 §3 的 PPA 合约规则。

### 5.3 阶段 2 的成本策略

**不能用阶段 1 的 LP 成本外推 SCUC。** 它含整数变量（机组启停）与跨时段状态（爬坡、最小启停时间），复杂度差一个量级。

建议顺序：

1. 1 小时 SCUC（无跨时段约束）→ 基线开销
2. 4 小时 → 跨时段状态的增长
3. 据此外推 24 小时与 168 小时

`results/logs/` 有 20 个未完成的 SCUC attempt（v3/v4/repair_001–010），多数跑满数小时后人工终止，或 cold-start 导致 `BestSol=-inf`。**这不是模型错误，是规模与预算不匹配。** 阶段 2 前必须先做上述有界实测。

如果 4 小时就要几十分钟，168 小时不可行，方案改为"阶段 1 的 LP 容量 + 声明的启停规则"，并在论文里明写该限制。
