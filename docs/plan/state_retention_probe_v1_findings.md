# 方案A保活检验：部分机制保留，强制关闭解释收缩

2026-11-09。DRAFT_NONAUTHORITATIVE，formal_result=false。合成条件可行性诊断，不是实际协议履约或已成立创新。

## 结果

在相同可用功率上限与信息集下允许暂停保活，1908个固定任务/通知/容量实例中有94个从不可履约变成可履约。实际取电由控制动作决定，可以不同。事件batch功率0.5足以覆盖假设的0.25保活功率时，通知长短不再改变接纳边界；只有供电低于保活门槛、确需丢失状态的区域，保存与通知继续产生差异。异步与同步保存的接纳结果在本网格全部相同。

因此原先“低Firm导致大量回滚”不能泛化到所有柔性接入。可保留的候选对象是具有状态保留条件的履约边界；现有证据仍不足以支持TSG级新方法或可迁移贡献。

## 一个具体合同菜单例子

初始未保存进度0，R=11，暂存10分钟再落盘5分钟，正常batch功率在第30分钟由1升到2，截止第60分钟。基荷1，batch保活0.25。事件发生在第20—30分钟。

|通知提前量|强制关闭：最低batch Firm|允许保活：最低batch Firm|
|---|---:|---:|
|0分钟|1|0.5|
|10分钟|1|0.5|
|20分钟|0|0|

这是离散菜单的最低可行档位。总Firm另加基荷1；未验证连续最小值。保活让零通知下可选较低档位；若提前量足以完成持久化，还可接受事件batch供电为0。故通知—Firm替代在此模型仍存在，但解释从“柔性功率必关机”收缩为“低于明确保活门槛时需要提前保护状态”。高Firm也降低削减义务，不能宣称同MW电网响应下的免费收益。

每种控制域212个任务/阶段上下文中，0→20分钟通知有24个上下文降低菜单Firm档位，其余无下降；没有最高档仍不可行而靠通知变可行的上下文。212和24为固定网格计数，不是经验概率。

## 为什么异步没有额外接纳收益

在事件功率足够保活的区域，本单任务模型没有后续掉状态风险，也不要求中间持久化。保存会占资源，而直接执行已足以达到乐观容量边界，因此同步或异步都不增加可接纳工作。

事件功率为0时，CPU/存储支撑也不足，必须在事件前完成持久化；仅GPU暂存完成不够。本网格异步没有产生额外整数R的可行点；已保留的边界见证也未采用save_async动作，不能据此声称实证覆盖异步收益。这是离散参数与单任务设定的观察，不是异步保存通常无价值的定理，也不代表不同落盘耗时、更细粒度工作量、多任务或多事件的结论。
