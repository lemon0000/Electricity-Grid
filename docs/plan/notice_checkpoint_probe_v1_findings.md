# 方案A核心机制测试：通知、暂停准备与阶段恢复

## 结论

方案A属于业务柔性的电网兑现问题。在声明的合成假设下，本轮机制可行性诊断为正：通知是否足够完成保存、当前未保存进度和阶段恢复供电，会改变同一原期限下可接纳工作量。补强JIT基线与精确搜索在全部已评估实例一致，因此不支持新算法优越性，也不应仅以弱基线违约支持TSG贡献。独立审查后的有效状态域为1752项，见末节。

## 设计与结果

12个5分钟步，事件在t4/5，保护负荷不变，batch必须暂停；正常供电总上限2，升级后3，保护负荷占1。任务可用执行速率由剩余供电决定，最大2。事件通知提前0/1/2/4步，保存耗时1/2步；初始未保存有效工作0/1/2/3单位；升级在t6/8/10；初始剩余工作0..18。任务期限保持t12，不因回滚延期。

通知前各方法严格共用固定周期保存规则。精确参考只在收到通知后搜索，不提前知道事件。保存消耗时间与功率；未完成保存遭遇事件会丢掉未保存进度；完成任务最终结果视为持久化。所有参数是声明假设，不套用15分钟阈值，也不引用为ERCOT/NGED实测。

## 可复核例子

初始未保存工作=0、保存耗时2步即10分钟；升级在t8即40分钟。通知提前0或5分钟时，可接纳剩余工作最大10单位；提前10或20分钟时，最大12单位。R=11、原期限与阶段路径完全相同：5分钟通知不可行，10分钟通知可行。失败由精确状态搜索而非一条启发式失败判定。

相同任务初始状态、10分钟通知、10分钟保存，恢复供电在t6/t8/t10升级时，最大R分别14/12/10。R=13时只有最早升级方案通过；这里阶段信息会改变接纳决定。

相同R=15、保存耗时5分钟、5分钟通知、t6升级，初始未保存进度0与3导致不同可行性（前者可行，后者不可行）。注意准备状态不能简单按初始age单调排序：较大age可能触发通知前常规保存，反而保护更多历史进度；必须连同规则和执行前史解释。

所有96组参数的最大R均低于18，因此扫描上端闭合；边界仅对整数R域成立，未声称连续最优边界。

## 对论文的含义与限制

声明合成假设下的机制诊断有正结果；新颖性和真实参数适用性尚未建立。原始供电功率上限仍可表示为标量，新增影响来自未保存进度与暂停动作对有效工作/期限的联系，不能写成“标量供电表示在物理上失效”。

本轮只有一个任务、一个事件、声明阶段恢复供电，没有多任务SLA、实际Firm-to-Firm容量转换、合同不确定性或CFE，也不证明级联违约。通知前只有一条固定策略，并未设计事件未知时的全局最优准备策略；通知后的DP仅是条件可行性参考。原模型与正式gate不变。

值得保留的候选主张是“通知条件与任务准备要求会改变阶段可接纳业务/所需资源”，而非“阶段感知新算法击败标准调度”。若继续研究，应先把这一决策问题与现有checkpoint/需求响应最近邻做同定义比较，再决定多任务与合同族的最小扩展。

## 独立只读开发审查与有效域修正

独立审查静态重放7296条保存轨迹，剩余工作、回滚、保存进度、功率和期限检查零违规。不是official sealed review。原设计中R=0但age>0的72项没有清楚定义已完成任务与未保存进度的关系，不计入有效科学案例；限定R=0⇒age=0后，有效1752项。通过数修正为blind=760、首轮greedy=766、精确/JIT=1158；最大R边界和上述示例不变。原报告、原契约字节保留，派生更正为valid_domain_summary.json，由notice_checkpoint_domain_audit_v1.py生成。

原“收到通知尽早保存”规则另有30项比blind更差，说明过早保存也会浪费时隙；不能把838比832的净计数当成可靠策略优势。“标准规则”在本报告仅指可解释的补强JIT基线，不是某份已核文献算法。JIT与DP共享状态转移，独立审查对保存见证做了重放，但不据此声称一般物理最优性定理。
