# 可信参数下的状态损失区：首轮证据筛查

2026-11-10。DRAFT_NONAUTHORITATIVE。回答：合理控制仍无法保护任务状态的区域，是否已获现实证据支持？本轮为来源与适用性筛查，不运行合成网格，不改旧模型、结果或协议。

## 结论

**当前结果为未决，不能判为存在，也不能判为不存在。** 当前可取得的公开资料没有提供同一站点、同一设备与同一次调用的完整参数闭包。更重要的是，本轮找到更新的接入政策，表明此前通用柔性接入叙述不能直接作为当前新建爱尔兰数据中心案例。

因此，现有demo的状态损失正例保持为合成机制，不能升级为可信站点实证。也没有证据支持“保活功率总是够”。下一步应先固定合同适用对象与实际状态保护路径，再做参数筛查；不以任意Firm比例和单卡idle假设拼成可信正例。

## 一、此次新增的适用性核查

[EirGrid当前需求接入入口](https://www.eirgrid.ie/industry/becoming-customer/demand-connections)指向[Data Centre Connection Offer Process and Policy Version 3，2026-05-20](https://cms.eirgrid.ie/sites/default/files/publications/Data-Centre-Connection-Offer-Process-and-Policy-V3-May-2026.pdf)。核对其§1、§2.1、§2.3、§2.4及§2.7：

- 文件说明其适用的新输电接入申请范围，并替代旧版；受限区域申请不能按该流程推进。
- 要求与负荷规模相衔接的配套发电/储能；负荷与其交付进度须匹配。
- 部分要求涉及独立接入和计量，不能把配套容量自动视为站内可孤岛保活电源。

这使“新建数据中心先在受限区域获取低Firm接入、供电不足而回滚”的爱尔兰实例前提未通过适用性检查。历史协议、存量站点和其他法域须按各自条件另查；不是说所有柔性接入均不存在。上述是对本次所读政策文件的研究适用性判断，不是对每个存量项目的法律认定；文件自身注明可能随相关程序变化，采用时仍需核对项目合同。

官网同时链接[技术评估文件](https://cms.eirgrid.ie/sites/default/files/publications/Data-Centre-Technical-Assessment-May-2026.pdf)及[受限区域说明](https://cms.eirgrid.ie/sites/default/files/publications/Data-Centre-Constrained-Area-Overview-May-2026.pdf)。本轮成功打开其索引，但未将它们当作已校准的站点运行数据。ESB通用产品说明仍支持柔性接入结构，不能替代具体数据中心的适用性证据。

## 二、参数闭包逐项检查

|必须确定的量|已找到的依据|仍缺什么|筛查状态|
|---|---|---|---|
|实际调用上限、持续时间与响应期限|旧运行协议模板及通用接入说明|适用项目的签署条款与调用轨迹，版本/过渡安排|未决|
|可用于保护状态的剩余功率|Firm结构、配套资源政策|同一时刻关键业务与设施基荷、实际设定值、本地资源的可用性和供电拓扑|未决|
|暂停保活所需完整功率|EcoCenter证明暂停并保留显存可实现|目标GPU、CPU、内存、网络及必要设施共同维持状态的测量|未决|
|暂存与持久化所需时间/功率|PyTorch报告GPU停顿与CPU落盘分离|同一硬件和任务规模下的完整保存时间、各阶段供电范围|未决|
|任务暴露状态与原期限|合成模型有明确age和期限|真实任务最后持久化时点、暂停/迁移权限、恢复时间、原SLA|未决|

任一路径能及时保护必要状态，就不能把任务归入“必然状态损失”。仅当所有实际允许的路径均被排除，并有相应功率、时间、容量或权限证据，才可确认该情形进入状态损失区。参数不全时保持未决；固定策略失败也不等于不存在其他可行控制。

## 三、已有数字为何还不能填满闭包

### 3.1 GPU功率比例不是全站保活阈值

[ASI公开模型](https://arxiv.org/html/2609.05406v1)的allocated-GPU idle中心比例为0.20、敏感性范围0.15—0.25。它是重建功率模型的参数范围，含跨硬件测量锚点，不是目标数据中心在暂停状态下的完整支撑功率置信区间。小时数据也不能校准分钟级响应和保存过程。

因此不能把“Firm比例低于20%”作为可信状态损失判断；分母、设备范围、设施基荷和其他供电路径均不相同。旧参数包中的范围保留其原始属性，不转为实测门槛。

### 3.2 保留显存已有实现证据，但完整设施门槛未知

[EcoCenter，§4.5及§5.1.1](https://arxiv.org/html/2601.22487v1)在8张MI50服务器上通过暂停kernel发射保留显存状态。论文的约60W调制瓶颈不是整机或设施保活需求。它能排除“所有削减都必须回滚”，不能证明所有站点的Firm均足以保活。

### 3.3 更快的GPU暂存会改变通知阈值

[PyTorch/IBM技术说明](https://pytorch.org/blog/reducing-checkpointing-times/)报告特定7B模型GPU停顿从148.8秒降为6.3秒；CPU到磁盘的持久化在后续完成。既不能把6.3秒当完整关停准备时间，也不能把demo暂存10分钟再落盘5分钟作为普遍可信参数。

demo的20分钟通知效应由其合成时长和控制范围产生，尚未得到该真实任务参数支持。

## 四、三个命题的当前判定

|命题|判定|原因|
|---|---|---|
|可信场景存在无法保护状态的区域|未决|缺少合同—硬件—任务—本地供电的配对闭包|
|可信场景下状态总能保住|未决|保活实现与配套容量义务不证明所有时刻的可用性、连通性或时间充分性|
|存在有决策分量、相对已有方法独立的贡献|未决|首先要确认适用场景；现有合成边界只支持条件机制，尚无同定义近邻比较|

已获得的实质否定结果是：**不能用当前已查的爱尔兰新申请流程直接实例化原来的低Firm回滚故事，也不能用ASI idle范围直接校准保活门槛。** 这不是对所有法域或既有站点的否定。

## 五、后续最小证据包

先选定一个适用对象：具体存量合同、明确允许柔性接入的数据中心项目，或另一个已确认适用的法域。其后收集同一规模下的三条控制路径：显存保留、主存暂存、持久化后关停。每条路径需记录必需功率、持续时间、介质容量、可用硬件及供电来源。

若无法取得配对站点记录，可开展文献锚定的情景分析，但必须将项目合同、硬件测量和其余假设分列。选择规则先于目标结果固定，保留全可保活、不可保活和未决区域。正式运行前另写模型与预算合同；本文件没有启动新实验。

若在充分覆盖且预先声明的范围内全部能保护状态，应转向保活条件下的期限/接纳决策。不能把有限扫描的空结果升级为“现实中不存在状态损失”。
